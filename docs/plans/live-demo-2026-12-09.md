## Weak points, most dangerous first

1. **No run and no evaluation yet.** Executor, L2 and L3 items, evaluators and the results screen are all missing, with 13 days left. *Roles 7, 6, 5, 3; the glue is role 2.* Get the smallest path through first (L0 and L1, one model, `none` and `gold`, results in the web), then add L3 and L2 to it. A level that is not ready is shown as unavailable, not hidden.
2. **Building the XML of a random project.** `sphinx-build -b xml` needs the project's docs dependencies and imports the library (autodoc); its extensions may not support Sphinx 9.x; a build can take minutes; and it never runs on our VM (SPEC §1.1). Today each library needs a hand-written case. *Role 1.* A `workflow_dispatch` workflow in our repo that builds any public repo + ref on a GitHub-hosted runner into an XML artifact with `build-env.txt`, tried on at least 10 projects. Keep a few pre-built projects as a fallback.
3. **Getting the inputs into our service live.** An upload needs an OIDC token from the registered workflow of a registered repo (SPEC §11). A random repo is neither. *Roles 1 and 2.* Decide by 2026-12-02: fork into our organization with our workflow and `notinspec db add-project`, or run the CLI on the VM (`notinspec demo`) into the same run folder the web reads.
4. **Time and rate limits on stage.** Groq free tier: 1 000 requests/day and 8 000 tokens/min per model, and a `gold` prompt has a few thousand tokens, so a few items per minute (SPEC §8). Claims and NLI are slow (above). A whole project in 3 modes does not fit a live slot. *Roles 7 and 4.* A demo profile with caps: N items per level, a sample of chunks for claims, `none` and `gold` only, one model. Measure the whole run in rehearsals and fit it in the time we have.
5. **Unseen documentation.** Tested on three libraries only. A random project may have no API reference (narrative docs only, so no `Signature` and no L1 or L3), use another domain (C, JavaScript), have nodes the reader does not know, or have thousands of sections. *Role 4.* Rehearsal corpus of 10–20 Sphinx 9.x projects; every failure is either fixed or shown as "unavailable" with the reason, never a crash.
6. **L3 depends on examples, constraints and parsing answers.** Adaptation and variation need `Constraint`s, which are not extracted yet. Model answers come with fences, imports, aliases and partial code. *Roles 6, 4 and 7.* For the demo, copy and variation from signatures may be enough; the answer parser is tested on recorded real answers.
7. **L2 is new.** Questions from grounded claims and their evaluation do not exist. *Role 5.* For the demo: questions from `kept` claims, evaluation by NLI; the LLM judge and perturbation after the demo.
8. **One model under test, and a preview.** `qwen/qwen3.8-27b` is a Groq preview that Groq may withdraw (SPEC §18). *Role 7.* Probe a second model (`notinspec models --probe`) and configure it before the demo.
9. **Deploying right before the demo.** `main` auto-deploys, five DEPLOY PRs are open, and the VM has 4 vCPU with the NLI model taking ~3 GB (SPEC §6.4). *Role 1.* Freeze `main` on 2026-12-07, rehearse on the deployed VM, keep the last good image tag to roll back to.

The demo may stay on run folders (`run.json`) like today's demo. Results in Postgres can follow after it.
